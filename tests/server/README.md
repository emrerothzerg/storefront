# tests/server
QA-owned server-side integration tests (repositories, services, server actions against a real SQLite database), run with `bun test`. Owning task: T26 (qa-engineer). Implementers put their unit tests next to the code under `src/`, not here.

## QA adversarial tests for T08 / T10

- `session.qa.test.ts` (T08): mocks `next/headers` with `mock.module` at the top of the file, then `await import()`s `@/server/session/session`. The mock delegates to a per-test `currentCookies` factory, so tests can install broken stores (`cookies()` resolving `undefined`, `get` missing or throwing, `set` throwing). Covers NUL-byte, mixed-case, wrong version/variant, oversized and injection-shaped cookie values, cookie option objects per `NODE_ENV`, and a static check for the "must not be called from render" doc comment. Documented behaviour: `getOrCreateSessionId()` rejects with the store's error when `set` throws (allowed), and parallel cookie-less calls each mint a separate id.
- `payments.qa.test.ts` (T10): builds cards with `validateCard` (fixed `now`). Covers 100x determinism per magic card, 50-way concurrent same-key calls with mixed cards (with and without `latencyMs`), key reuse after `reset()`, amount edge cases (`1e3` ok; `1e21`, `-0`, non-numbers rejected), 19-digit and spaced cards, `Object.isFrozen`, a leak scan (no 6+ digit run, CVC or name in results, `listCharges()`, logger output or `Bun.inspect` of the provider), no console output, no network, no third-party imports, no module-level instance.
- Bun's `mock.module` is process-wide and `mock.restore()` does not undo it. Both this file and `src/server/session/session.test.ts` mock `next/headers`; they pass together in either order because each registers before importing.

## QA adversarial tests for T09 (cart repository + service)

- `cart.qa.test.ts` (T09): every test wires `createDatabase(":memory:")` + `runMigrations` + `seedProducts` + `SqliteCartRepository` / `SqliteProductRepository` / `new CartService({...})` explicitly; persistence is asserted by querying `carts` / `cart_items` directly. Covers criteria 1-8 with boundaries (stock exactly reached / stock+1, 99 vs 100 and cumulative 99+1, `-0`, `1e2`, `Infinity`, `"2"`, bigint, arrays at the type boundary), the orchestrator rulings (fail-not-cap with `{ productId, available, requested }`, `setQuantity` upsert, `ABOVE_MAX`, stored-quantity `itemCount`, `INVALID_INPUT` / repository `TypeError`, stubbed-deleted-product placeholder), 25 concurrent adds on stock 3, mixed concurrent ops over two connections to a temp file DB, SQL-shaped session and product ids, reduced / unavailable / price-changed reads, `getTotals` vs `getCart` consistency, byte-identical snapshots (incl. `updated_at`) after every failed mutation, a 600-step seeded random op sequence checking `0 < quantity <= stock`, `<= 99`, integer type and no orphan lines, and JSON round-trips.
- D1 (fixed, now regression tests): a `null` quantity used to bypass `validateQuantity` (`mutate()` used `null` as its "no quantity" sentinel). The three `D1 regression` tests require `INVALID_QUANTITY` / `NOT_A_NUMBER` with no mutation on existing and new lines; `nit 1` / `nit 2` pin the clamped `INSUFFICIENT_STOCK` message and the constructor `TypeError` for an invalid `maxQuantity`.
- The temp file DB lives under `os.tmpdir()` and is removed in `finally`; nothing touches `./data`.

## T11 / T26 (orders, and cart -> orders -> payments integration)

- `orders.qa.test.ts` (T11): each test wires `createDatabase(":memory:")` + `runMigrations` + `seedProducts`, `CartService`, `SqliteOrderRepository`, a fresh `MockPaymentProvider` (or an injected stub: throwing, rejecting, custom-message, never-resolving) and a fresh `InFlightRegistry` into `new OrderService({...})`. Covers criteria 1-9 and the orchestrator rulings: hostile address/card shapes (null, arrays, prototype-less, `__proto__`, huge strings, a throwing Proxy), every `MOCK_CARDS` outcome, same-key replay after paid/failed, new-key retry, key lengths 0/1/128/129, non-ASCII/control keys, same key across sessions (sequential and concurrent), `getOrder` with upper-case/foreign/malformed/SQL-shaped ids, snapshot immutability after product edits and deletion, `failureCode` iff `payment_failed`, JSON round-trips, a cross-process duplicate race (two services, separate in-flight maps) and 20-iteration loops of the last-unit and duplicate-key races. The never-resolving provider is raced against a 50 ms timer and then released, so the suite cannot hang.
- `integration.qa.test.ts` (T26): full flows through `CartService` -> `OrderService` -> `MockPaymentProvider` (browse/add/update/remove/checkout, decline then new-key retry, stock lowered after add, cross-session isolation), a 20-iteration full-flow race loop, the error-code coverage matrix over `ERROR_CODES` (unreachable: `ORDER_NOT_FOUND` by design), a seeded (mulberry32) 250-cart totals property test checked exactly with BigInt, a leak scan over `orders`/`order_items` rows, all results, `listCharges()`, provider logs, captured console output and `Bun.inspect(service)`, and a negative control for the scanner.
- Leak-scan rule (orchestrator ruling): strip UUIDs, then flag the exact card numbers used (plain and 4-4-4-4 spaced), the CVCs used (4-digit values starting with `0`, so they can never occur inside a JSON number), runs of 9+ digits, and the keys `"number"`, `"cvc"`, `"expMonth"`, `"expYear"`. `VALIDATION_FAILED` results name card fields as keys by design, so for those only values are scanned. The property test skips the 9+ digit rule because its random totals legitimately exceed 9 digits.
- D-T11-1 and D-T11-2 are fixed and are now regression tests (the "T11 defect regressions" describe block). D-T11-1: an overflowing cart total returns `MONEY_OVERFLOW` ("This order total is too large to process.") with nothing reserved, charged or ordered, for both a single line and a cross-line subtotal; the integration matrix now counts `MONEY_OVERFLOW` as reachable, and only `ORDER_NOT_FOUND` is unreachable. D-T11-2: 80k-char padded fields and 1 MB strings in every address/card field are handled in under 250 ms, and a Proxy probe checks that validation runs outside any transaction.
